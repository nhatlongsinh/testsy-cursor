# Release the integration package

Package version: `package.json`. Client manifests and Registry metadata take that version during parent config generation. The CLI retains its own canonical version and is copied byte-for-byte into the release; `dist/release.json` records its SHA-256.

1. In the parent application checkout, run `npx tsx scripts/v11/config-gen.ts --check` from its root. Then run package `npm run check` and `npm run build`. Parent checks must also cover any source CLI change. In a standalone source checkout, generated manifests and CLI are reviewed release inputs; the package checks/build work without the parent repository. A native client package has no build toolchain: use the source package for rebuilding. Preserve the source package in its commit.
2. Install each generated client package in a clean client profile, using a dedicated, scoped Testsy key. Record client/version, tool discovery, skill discovery, one permitted read, one authorized run, result polling and an authentication-failure case. Verify that secrets do not enter logs. Revoke the key afterward. No live-client proof is implied by local tests.
3. Use the [example prompts](examples/prompts.md) for a demonstration: request → confirmed checklist → run → per-check evidence → unchanged rerun after fix. Record the actual UI and outcome. Use synthetic data; obtain consent before publishing customer results. A diagram or static mockup is not a real test screenshot.
4. Run `npm run export` in the source package. It creates separate repository roots under `release/` and an `export.json` file with SHA-256 inventory. `release/source` is the standalone integration source; the other target folders are native client/action/catalog roots. Only explicitly allowlisted source files and built package files are copied. Review the inventory, then copy the chosen root to a new repository outside the private application checkout before initializing Git. Do not publish the parent application repository, its Git history, engine, private records, environment files or artifacts. Keep the integration MIT license. Add the real repository URL to listing metadata when it exists.
5. For Claude, publish the built marketplace repository; users can add its actual GitHub address. For Cursor, submit the native package repository for review. For Gemini, put `gemini-extension.json` at the repository root and add the `gemini-cli-extension` topic. For skills discovery, publish the canonical `skills/` source in the public integration repository and use that actual repository in installation instructions.
6. For the GitHub Action, publish `dist/action` as a repository with root `action.yml`, review its packaged CLI hash, create a version tag and complete the GitHub Marketplace listing flow. Test the real workflow on a sandbox before advertising it.
7. For the MCP Registry, validate `server.json` with the current official publisher tooling. Authenticate ownership of `testsy.dev` using the publisher's DNS or HTTP method, then publish the `dev.testsy/testsy` remote metadata. Keep publishing private keys and login tokens outside the package. Registry publication does not automatically publish into other directories.
8. For ChatGPT/Codex and Claude hosted directories, first prove deployed OAuth discovery, S256 PKCE, exact redirect validation, explicit workspace consent, scope enforcement, refresh-token rotation, revocation and workspace isolation. Install the OAuth candidate in a clean supported client. Submit the remote server and relevant skill bundle through each official portal, provide actual review evidence and accessible required listing assets, and resolve review findings. Do not label the candidate approved or publicly installable before publication is confirmed.

For direct downloads, run `npm run archives` to create deterministic tarballs under `release/archives/`. Verify `shasum -a 256 -c SHA256SUMS` from that folder, then extract the selected archive with `tar -xzf testsy-<target>.tar.gz`. In the parent application checkout only, `npm run downloads` writes those files to `apps/landing/public/downloads/testsy/`; the landing deployment makes them available under `/downloads/testsy/`. No API key, live client, directory submission or Git publication is invoked by either command.

Format sources: [OpenAI submission](https://developers.openai.com/plugins/deploy/submission), [Claude publishing](https://claude.com/docs/directory/publish), [Cursor publishing](https://cursor.com/marketplace/publish), [Gemini releasing](https://geminicli.com/docs/extensions/releasing/), [MCP Registry authentication](https://modelcontextprotocol.io/registry/authentication), [GitHub action publishing](https://docs.github.com/en/actions/how-tos/create-and-publish-actions/publish-in-github-marketplace).
